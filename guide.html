在 Mac 上跑一个「只做选择、不写作文」的 AI 模型

Run an AI model on your Mac that picks answers instead of writing them

nanojev-mlx 把 NanoJev —— 一个 0.6B 的「并行决策模型」—— 移植到 Apple 芯片上原生运行。你给它一段状态和一个问题 + 几个候选选项， 它一次前向就返回一个完整的概率分布，全程不生成任何 token。

nanojev-mlx ports NanoJev — a 0.6B “parallel decision model” — to run natively on Apple Silicon. Give it a state and a question with a few candidate options; it returns a complete probability distribution in a single forward pass, with zero token decoding.

1 一句话理解它和 ChatGPT 的区别 The one-sentence difference from ChatGPT

普通大模型是「写答案」：一个字一个字往外吐，所以可能跑题、可能编造、 也无法告诉你「我有多确定」。NanoJev 是「打分」：候选选项是你给的， 它只负责给每个选项算一个概率。

打个比方 不是让学生写一篇作文，而是把选择题给他，要求他不仅要选，还要为每个选项标注信心百分比。 他不可能写出选项之外的答案——因为压根没有这个自由度。

这带来三个直接好处：

  • 不会格式错乱——输出永远被限制在你给的候选集合内。
  • 可解释——拿到的是完整概率分布，不是一句难以验证的断言。
  • 快且省——没有逐 token 解码循环，一次前向算完。

典型用途：工单该分给哪个团队、这句话是真是假、某个指标算几级。

A normal LLM writes an answer: token by token, so it can drift, invent facts, and cannot tell you how confident it is. NanoJev scores instead: the candidates are yours, and the model only assigns a probability to each one.

An analogy It is not an essay question — it is a multiple-choice question where the student must also write down a confidence percentage for every option. It cannot answer outside your candidate list, because that freedom simply does not exist.

Three immediate consequences:

  • No malformed output — the result is always inside the candidate set you supplied.
  • Inspectable — you get a full probability distribution, not an unverifiable sentence.
  • Fast and small — there is no token-by-token decode loop; one forward pass does it all.

Typical uses: routing a ticket to the right team, deciding whether a claim is true, grading a level.

2 一次推理到底发生了什么 What actually happens in one inference

  1. 拼路径把「状态 + 问题 + 每个候选」拼成 N 条独立的 token 序列，末尾统一加上 Decision: 与 EOS。
  2. 一次前向N 条路径右填充成一个矩阵，喂给 28 层的 Qwen3-0.6B backbone，只跑一遍。
  3. 取向量每条路径取最后一个真实 token 位置的 hidden state（1024 维）。
  4. 决策头打分一个 20 万参数的小网络给每条候选算出一个 logit；choice 题型还会让候选之间互相「看一眼」（集合内自注意力）。
  5. softmax把 logit 变成概率分布，直接作为答案返回。
为什么不写自定义注意力算子？ 因为 padding 永远在真实 token 的右侧，纯因果掩码下真实位置根本注意不到它。 所以「右填充 + 因果掩码」与 HF 的「因果 + padding 双重掩码」在数值上完全等价—— 这省掉了一整个自定义 kernel。
  1. Build paths — stitch “state + question + each candidate” into N separate token sequences, each ending with Decision: and EOS.
  2. One forward pass — right-pad the N paths into a single matrix and run the 28-layer Qwen3-0.6B backbone exactly once.
  3. Take the vectors — read the hidden state (1024-dim) at the last real token of each path.
  4. Head scores — a 200K-parameter head turns each candidate into a logit; for choice questions the candidates also attend to each other (a small set-attention).
  5. Softmax — logits become a probability distribution, returned as the answer.
Why no custom attention kernel? Padding always sits to the right of real tokens, so under a plain causal mask no real position can attend to it. “Right-padding + causal mask” is therefore numerically identical to HF's “causal + padding mask” — which removes an entire custom kernel from the port.

3 这个模型有多大：99.97% 是现成的 backbone How big it is: 99.97% is an off-the-shelf backbone

NanoJev 不是从零训练的模型。它的绝大部分就是公开的 Qwen3-0.6B，真正的「新东西」只有末端一个极小的决策头：

NanoJev is not trained from scratch. The vast majority of it is the public Qwen3-0.6B; the only genuinely new part is a tiny decision head on the end:

决策头本身就四步，全是小矩阵乘法：LayerNorm → 每候选一个标量 logit → 候选集合内做一次 4 头自注意力 → 输出一个 tanh 残差修正量。 因为要改的只有这个小头，移植才可能做得又快又准。

The head itself is four small steps: LayerNorm → one scalar logit per candidate → a single 4-head self-attention across the candidate set → a tanh residual correction. Because only this small head had to be rewritten, the port could be both fast and exact.

4 三种题型，共用同一次前向 Three question types, one shared forward pass

Type 你给什么What you provide 你拿回什么What you get back
boolean 一句待判定的命题A proposition to judge p_true 与 valuep_true and value
choice 2–255 个候选（id → 描述）2–255 candidates (id → description) 每个候选的概率 + 最高者A probability per candidate + the argmax
score 2–10 个有序等级描述2–10 ordered level descriptions score（期望值）与 levelscore (expectation) and level

boolean 的实现很巧妙：只有一条语义路径，logits 被构造成 [0, z]， 于是 p_true = sigmoid(z)。score 则对有序等级做 softmax 后取期望值—— 所以 「严重度 2.35 级」这种连续值也能表达，而不是硬塞进某一档。

boolean is neat: there is one semantic path and the logits are built as [0, z], so p_true = sigmoid(z). score takes the expectation over a softmax of ordered levels — so a continuous value like “severity 2.35” is representable instead of being forced into one bucket.

5 这个移植到底改了什么（以及没改什么） What the port changed — and what it deliberately did not

先说清楚一件事 One thing to get straight first 原版 NanoJev 以 CUDA 为先：它的推理脚本没有 CUDA 会直接报错退出， 记录的训练环境也面向 A100、bf16 精度，研究脚本大多限定 CUDA。 为了做同口径对比，本项目基准只移除那一处设备门禁——仅此一处， 原仓库其余代码一行未动——让同一份脚本能跑在 PyTorch MPS 上， 也就是基准表里的「PyTorch + MPS」那一列。 真正的差别在于：那条路必须装 PyTorch，而且内存和启动开销大得多。 The original NanoJev is CUDA-first: its inference script refuses to run without CUDA, and the recorded training environment targets an A100 in bf16. To get a like-for-like baseline, this project's benchmark removes only that device gate — one change, nothing else in the original touched — which lets the very same script run on PyTorch MPS. That is the “PyTorch + MPS” column in the benchmark table. The real difference is that this path forces PyTorch on you and costs far more memory and startup time.

模型本身一个字节都没动：权重、分词器、提示构造、概率语义全部照旧。

Not a single byte of the model changed: weights, tokenizer, prompt construction, and probability semantics are all untouched.

最需要小心的一块 The part that needed the most care prepare_examples——把状态、问题、候选集变成 token 路径的那段代码——是逐行移植的。 因为只要差一个 token，下游所有概率都会变，数值对齐验证也就失去意义。 prepare_examples — the code that turns a state, question, and candidate set into token paths — was ported line by line. A single differing token would change every probability downstream and void the equivalence check.

延迟 = 6 轮预热后的中位数；内存 = 峰值 RSS；冷启动 = 运行时导入 + 加载模型 + 首次出结果 （即跑 CLI 时用户真正要等的时间）；依赖 = Apple 芯片上 site-packages 的安装体积 （torch 对比 mlx + mlx-lm；两边都要装的 transformers、numpy、safetensors 相互抵消）。

这些数字可以用仓库自带的脚本一键复现： python benchmarks/benchmark.py --checkpoint-dir checkpoints/NanoJev --backend both --nanojev-repo ../NanoJev （--backend both 会把两个后端放进各自的子进程测量，避免内存读数互相污染。）

关于 1.3× 这个数字，说实话 它真实但不算惊艳，原因是结构性的：这个模型为每一条候选路径完整跑一遍 28 层 backbone。 所以算力瓶颈在 backbone，而不是本移植重写的那 20 万参数决策头。 MLX 在内存和启动上的优势（−44%、3.8×）远比延迟优势显著。 想让延迟再降一个量级，真正的抓手是前缀共享（见下一节），不是把决策头写得更快。

Latency = median of 6 warm rounds; memory = peak RSS; cold start = runtime import + model load + first result (what you actually wait for when running the CLI); footprint = installed site-packages size on Apple Silicon (torch versus mlx + mlx-lm; the shared transformers, numpy, and safetensors cancel out).

Reproduce all of it with the bundled harness: python benchmarks/benchmark.py --checkpoint-dir checkpoints/NanoJev --backend both --nanojev-repo ../NanoJev (--backend both measures each stack in its own subprocess so the memory readings stay clean).

About that 1.3×, honestly It is real but modest, and the reason is structural: the model runs the full 28-layer backbone once per candidate path. The workload is therefore compute-bound on the backbone, not on the 200K-parameter head this port rewrote. MLX's wins on memory (−44%) and startup (3.8×) are far more significant than the latency win. The real lever for a step change in latency is prefix sharing (next section), not a faster head.

需要 Apple 芯片 Mac（M1 或更新）、macOS 14 (Sonoma) 或更新、 Python ≥ 3.10，以及约 5 GB 磁盘（权重约 2.4 GB）。

                    "tokenizer/*", "backbone_config/*"],

PY

想读代码，建议顺序：text.py（先看懂一条候选路径长什么样）→ head.py（打分逻辑，最短最清晰）→ model.py（怎么把权重搬过来）→ predict.py + answers.py（怎么组装成结果）。

为什么 answers.py 要单独拆出来？因为 MLX 在无头、无 GPU 的环境里 导入即崩溃，把它隔离出去后，协议层才能在普通 CI 容器里跑起来。

Suggested reading order: text.py (see what a candidate path looks like) → head.py (the scoring logic — shortest and clearest) → model.py (how weights are moved over) → predict.py + answers.py (how results are assembled).

Why is answers.py its own module? Because MLX crashes on import in headless, GPU-less environments; isolating it is what lets the protocol layer run on an ordinary CI container.

9 它不是什么：诚实的能力边界 What it is not: honest boundaries

  • 不是通用聊天模型。它只回答你给的选择题。想聊天请用别的模型—— 这不是缺陷，是设计。
  • 只做推理，不含训练。原仓库的训练、评测、benchmark 流水线都没有移植。 本仓库负责把模型跑起来，不负责复现论文的训练数字。
  • 不含模型权重。权重约 2.4 GB，需自行从 Hugging Face 下载（见上一节）。
  • 无前缀共享。每条候选路径都从头跑一遍完整的 28 层 backbone，与原版一致。 同一问题下的候选其实共享很长一段前缀，缓存它是最大的优化空间， 但本移植为保证与参考实现逐步对齐，有意没有引入这个改动。
  • 仅 fp32，尚未量化。上游是在 A100 上用 bf16 训练的，本移植跑 fp32—— 这是一条不同的数值路径，更接近用于等价性验证的 CPU fp32 基准， 而不是论文公布的指标。MLX 支持 4bit/8bit 量化（内存可再降约 4 倍）， 但它会改变数值，需要单独一轮验证才能采信。
  • 未挂载官方前端。本仓库只提供推理与 HTTP 接口， 不含上游 web/ 里的演示站点。
  • Not a general chat model. It only answers the multiple-choice questions you hand it. Use another model to chat — that is a design choice, not a defect.
  • Inference only. The original repository's training, evaluation, and benchmark pipelines are not ported. This repo runs the model; it does not reproduce the paper's training numbers.
  • No weights included. The ~2.4 GB checkpoint is downloaded from Hugging Face yourself (previous section).
  • No prefix sharing. Every candidate path runs the full 28-layer backbone from scratch, exactly like the original. Candidates within a question share a long prefix, so caching it is the biggest available optimization — but this port deliberately left it out to stay step-for-step aligned with the reference implementation.
  • fp32 only, no quantization yet. Upstream trained in bf16 on an A100; this port runs fp32, which is a different numerical path — closer to the CPU fp32 reference used for the equivalence tests than to the published figures. MLX supports 4-bit and 8-bit quantization (~4× less memory), but that changes the numbers and needs its own validation pass before it can be trusted.
  • No bundled front-end. This repo ships inference and an HTTP interface only; it does not include the demo site from upstream's web/.

Metal Apple 的 GPU 接口。MLX 通过它把计算放到 Mac 的 GPU 上。 Apple's GPU API. MLX uses it to run compute on the Mac's GPU.
backbone 主干网络。这里是 Qwen3-0.6B，负责把文本变成向量，占 99.97% 的参数。 The main network — here Qwen3-0.6B, which turns text into vectors and holds 99.97% of the parameters.
decision head 决策头。接在 backbone 后面的小网络，把向量变成每个候选的分数。 The small network on top of the backbone that turns vectors into a score per candidate.
logit softmax 之前的原始分数，可正可负、不要求和为 1。 The raw score before softmax — can be any real number and need not sum to 1.
softmax 把一组 logit 变成概率分布（全部 ≥ 0 且和为 1）的运算。 Turns a set of logits into a probability distribution (all ≥ 0, summing to 1).
自回归解码 普通 LLM 逐 token 生成答案的过程。本项目完全不涉及（0 步）。 The token-by-token generation loop of a normal LLM. This project does none of it (0 steps).
hidden state backbone 每一层输出的向量。这里取每条路径最后一个真实 token 的 1024 维向量。 A vector output by a backbone layer. Here: the 1024-dim vector at each path's last real token.
因果掩码 让每个位置只能看到自己及左侧内容的掩码，保证不会「偷看」未来 token。 A mask letting each position see only itself and what precedes it, so it cannot peek at future tokens.
前缀共享 同一问题下的候选共享一段相同前缀，缓存其计算结果即可省掉重复计算。本项目尚未实现。 Caching the common prefix shared by a question's candidates to skip recomputation. Not implemented here.
量化 用 4bit/8bit 等更低精度存权重以省内存，代价是数值会变。本项目尚未启用。 Storing weights at lower precision (4/8-bit) to save memory, at the cost of changing the numbers. Not enabled here.
fp32 / bf16 两种浮点精度。fp32 更精确更占内存，bf16 更快更省。本项目用 fp32。 Two floating-point precisions. fp32 is more exact and heavier; bf16 is faster and lighter. This port uses fp32.

正确性数字（40 项测试全通过、最大概率偏差 1.56e-07、hidden state 误差 1.006e-04） 已在 Apple M4 / 16 GB 上实测复核；性能数字取自仓库自带的 benchmarks/benchmark.py，可用上文命令一键复现。 完整说明见 README.zh-CN.md 与 examples/request.json。

Correctness numbers (19/19 tests passing, max probability deviation 1.56e-07, hidden-state error 1.006e-04) were re-measured on an Apple M4 / 16 GB. Performance numbers come from the repo's benchmarks/benchmark.py and reproduce with the command above. Full details in README.md and examples/request.json.
